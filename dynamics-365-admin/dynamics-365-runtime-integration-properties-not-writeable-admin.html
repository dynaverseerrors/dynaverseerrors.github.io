                The table below is the fact sheet for this fault; the sections after it follow the same order support teams use. Everything here applies to Dynamics 365 environments, and the decimal form of the code is included because server logs rarely print the hex form.

                What Causes Runtime Integration Properties Not Writeable

                The message text is the best clue. “RuntimeIntegrationProperties attribute is not writeable. Please remove this attribute from the payload and try again. Solution unique name: {0},…” means the platform evaluated a condition and rejected the operation before any data could be written or returned. Metadata-related causes are likely: the definition of a table, column, or relationship changed, and something that referenced the old definition now fails validation.

                • Client-side state is stale: cached metadata, an old session token, or an outdated form script sends values the server no longer accepts.
                • The signed-in user, service account, or integration app does not hold the exact privilege combination required for this operation.
                • A recent change — a solution import, a role edit, a new plug-in step, or a process change — altered the state the platform now checks.

                Reports phrased as “dynamics 365 admin center 0x80090308” describe the identical fault in different wording.

                A closely related walkthrough — S2 S Access Token Cannot Be Acquired (Error 0x8005E243): Dynamics 365 Admin Checklist for Security Roles and Settings — follows the same first three checks and is worth keeping open in a second tab.

                Quick Fix for 0x80090308

                For a fast path, work through the four checks below — they resolve the majority of 0x80090308 reports without touching configuration:

                1. Retry the operation once after a short pause — transient platform conditions clear on their own.
                2. Sign out, close every browser tab of the app, reopen it, and sign back in with the affected account.
                3. Repeat the action in a private window or a different browser to rule out stale cached metadata.
                4. If it still fails, try the same action with a test account that has broader privileges — the result scopes the problem to either the user or the environment.

                If you arrived while searching “runtime integration properties not writeable business unit dynamics 365”, start with the first two steps above — they cover that exact case.

                Step-by-Step Fix

                If the quick fix did not clear the message, work through the full checklist. Each step either resolves 0x80090308 or produces the evidence an administrator needs for the next step.

                1. Collect the affected user, the exact timestamp, and the operation that failed; the admin investigation stands on these three facts.
                2. In the Power Platform admin center, open the environment and review the user's security roles against the failing operation — compare against a user who succeeds.
                3. Check business unit placement: role inheritance runs through the business unit hierarchy, so a correct role in the wrong unit still denies access.
                4. Verify that the feature or setting named in the message is enabled at the environment level, and whether a recent solution import or update changed it.
                5. Review the audit log around the timestamp for related configuration changes made by other administrators or automated deployments.
                6. Apply the least-privilege correction, then ask the affected user to retest immediately — do not grant broader rights than the operation requires.
                7. If several users hit the same fault, treat it as configuration drift: diff the current settings against your baseline and document the correction.

                For a second opinion on the admin-side checks, see Rule Already Exists With Same Queue And Channel (Error 0x8004F884): Dynamics 365 Admin Checklist for Security Roles and Settings, which walks the same environment review from a different error.

                Prevention and Best Practices

                Prevention is mostly about change hygiene: test solution imports in a sandbox first, keep security role edits documented, and watch environment health after major updates. Teams that follow a simple change log rarely see 0x80090308 twice for the same reason.
