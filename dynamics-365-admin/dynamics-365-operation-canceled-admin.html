This guide explains what triggers the fault, the fastest way past it, and the full checklist that administrators and developers use when the quick fix is not enough.

                The table below is the fact sheet for this fault; the sections after it follow the same order support teams use. Everything here applies to Dynamics 365 environments, and the decimal form of the code is included because server logs rarely print the hex form.

                What Causes Operation Canceled

                Faults like this one are raised deep in the platform pipeline, and the visible text “Refresh was canceled by user.” is a summary rather than the full story.

                • The record or object referenced by the request is inactive, locked by a process, or in a state that does not allow the operation.
                • A recent change — a solution import, a role edit, a new plug-in step, or a process change — altered the state the platform now checks.
                • A transient platform condition (throttling, replication delay, or a busy node) produced the fault once and retrying will simply succeed.

                Reports phrased as “dynamics 365 admin center 0x80060912” describe the identical fault in different wording.

                A closely related walkthrough — Operation Organization Not Fully Disabled (Error 0x8004D23a): Dynamics 365 Admin Checklist for Security Roles and Settings — follows the same first three checks and is worth keeping open in a second tab.

                Quick Fix for 0x80060912

                Before deep troubleshooting, run the quick sequence; it either fixes the issue or narrows it to a single layer:

                1. Retry the operation once after a short pause — transient platform conditions clear on their own.
                2. Sign out, close every browser tab of the app, reopen it, and sign back in with the affected account.
                3. Repeat the action in a private window or a different browser to rule out stale cached metadata.
                4. If it still fails, try the same action with a test account that has broader privileges — the result scopes the problem to either the user or the environment.

                If you arrived while searching “operation canceled business unit dynamics 365”, start with the first two steps above — they cover that exact case.

                Step-by-Step Fix

                The detailed sequence below goes layer by layer — client, account, configuration, and platform — so nothing is skipped. Expect five to ten minutes for the full pass.

                1. Collect the affected user, the exact timestamp, and the operation that failed; the admin investigation stands on these three facts.
                2. In the Power Platform admin center, open the environment and review the user's security roles against the failing operation — compare against a user who succeeds.
                3. Check business unit placement: role inheritance runs through the business unit hierarchy, so a correct role in the wrong unit still denies access.
                4. Verify that the feature or setting named in the message is enabled at the environment level, and whether a recent solution import or update changed it.
                5. Review the audit log around the timestamp for related configuration changes made by other administrators or automated deployments.
                6. Apply the least-privilege correction, then ask the affected user to retest immediately — do not grant broader rights than the operation requires.
                7. If several users hit the same fault, treat it as configuration drift: diff the current settings against your baseline and document the correction.

                Prevention and Best Practices

                To keep 0x80060912 from returning, add the failing operation to a lightweight smoke test after every deployment, and review role assignments whenever responsibilities change. Most repeat occurrences trace back to an undocumented change.

                FAQ

                What does 0x80060912 mean in Dynamics 365 security role?

                In Dynamics 365 security role, 0x80060912 signals that the platform rejected the operation with “Refresh was canceled by user.”. The Quick Info table above lists the exact decimal value your logs may show instead of the hex code. In logs and tickets this may appear as “dynamics 365 0x80060912 security role”.

                Is 0x80060912 safe to retry?

                Only after the cause is addressed. Retrying an operation that fails with 0x80060912 without changing anything usually produces the identical message; apply at least the quick fix before a second attempt. The same condition is often captured in searches as “dynamics 365 operation canceled permissions”.

                What does 0x80060912 mean in Dynamics 365 user access?

                In Dynamics 365 user access, 0x80060912 signals that the platform rejected the operation with “Refresh was canceled by user.”. The Quick Info table above lists the exact decimal value your logs may show instead of the hex code. Users who report “0x80060912 dynamics 365 user access” are describing exactly this error.
